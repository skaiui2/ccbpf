# ccBPF 编译器设计文档（前端 + IR + 后端）

## 1. 总体结构

编译器整体分为三层：

- **前端（Frontend）**：词法分析、语法分析、AST 构建、类型检查、符号表管理
- **中间表示（IR）**：结构化的三地址风格指令序列
- **后端（Backend）**：IR → BPF 指令序列（4.4BSD cbpf），并最终打包为 `.ccbpf` 镜像

典型流水线：

```text
C 源码
  → 词法分析（lexer）
  → 语法分析 + AST（parser + inter）
  → IR 生成（AST.gen / jumping）
  → IR 降级为 BPF（ir_lower_program）
  → 打包为 .ccbpf（ccbpf_pack_memory）
```

## 2. 内存管理与区域划分

编译器使用 **区域分配器（region allocator）** 管理生命周期：

- `frontend_region`：词法/语法分析阶段的临时对象
- `longterm_region`：AST、类型、符号表等长期存在对象
- `ir_region`：IR 链表
- `string_region`：字符串常量池
- `backend_region`：后端布局、跳转修补等临时结构

初始化入口：

```c
void compiler_init(uint8_t region_bit,
                   uint32_t cap,
                   uint32_t string_cap,
                   uint32_t ir_cap);
```

所有 AST / Type / IR 节点均通过 `mg_region_alloc()` 从对应 region 分配，不做细粒度 free，整体在阶段结束时销毁。

region 的句柄指向 `mg_region`。pool 模式按块大小分组，bump 模式在连续缓冲区上递增游标：
```c
#define MG_MAX_CLASS_BITS 12

enum mg_region_kind {
    MG_REGION_POOL = 0,
    MG_REGION_BUMP = 1,
};
```

```c
struct mg_pool_node {
    membit_pool_t pool;
    uint16_t      block_count;
    uint16_t      block_size;
    struct mg_pool_node *next;
};

struct mg_class {
    struct mg_pool_node *pools;
    size_t               block_size;
};

struct mg_block_header {
    membit_pool_t pool;
};

struct mg_bump_state {
    uint8_t *buf;
    size_t   cap;
    size_t   off;
};

struct mg_region {
    enum mg_region_kind kind;
    uint8_t             max_bits;

    union {
        struct {
            struct mg_class classes[MG_MAX_CLASS_BITS + 1];
        } pool;

        struct mg_bump_state bump;
    } u;
};
```

bump 分配先把长度向上对齐到四字节，检查 `off + size <= cap`，再返回 `buf + off` 并推进 `off`。pool 分配先选择大小类别，遍历该类别的池，池满时增加一个池。`reset` 复用内存；`destroy` 释放区域及其底层存储。

| 区域 | 保存对象 | 生命周期 |
| --- | --- | --- |
| `frontend_region` | 使用池分配的前端临时对象 | 函数外层每条语句生成 IR 后重置 |
| `longterm_region` | token、名称、类型、符号和多数语法节点 | `frontend_destroy()` |
| `ir_region` | IR 链表 | 后端转换完成后 `ir_free()` |
| `string_region` | 字符串常量 | 打包完成后 `bpf_builder_free()` |
| `backend_region` | 指令数组、标签表和待回填表 | `bpf_builder_free()` |
| `pack_region` | 序列化镜像 | `bpf_builder_free()` |

前端重置临时池时，IR 与长期节点仍然有效。字符串需要保留到打包阶段；镜像需要在释放 builder 之前写出、复制或加载。编译峰值由同时存活的区域及扩容缓冲区决定。

## 3. 词法、语法与符号系统

### 3.1 词法分析（lexer）

词法分析器与 token 的结构如下。`peek` 保存当前字符，`words` 保存关键字映射，token 的 `tag` 决定应读取名称、整数值还是标点字段：
```c
struct lexer {
    int line;
    char peek;
    char *filename;
    struct hashmap words;
};

struct lexer_token {
    int tag;
    int line;
    int int_val;
    float real_val;
    char *lexeme;
    char ch;
};
```

`struct lexer` 负责：

- 维护当前行号、peek 字符

- 关键字表 `hashmap words`（`if/else/struct/return` 等）

- token 类型枚举 

  ```
  enum tag
  ```

   覆盖：

  - 基本运算：`PLUS/MINUS/STAR/SLASH/MOD`
  - 比较：`LT/LE/GT/GE/EQ/NE`
  - 逻辑：`AND/OR/NOT`
  - 位运算：`AND_BIT/OR_BIT`
  - 标识符/常量：`ID/NUM/STRING/TRUE/FALSE`
  - 语法符号：`LPAREN/RPAREN/LBRACE/RBRACE/COMMA/SEMICOLON/LBRACKET/RBRACKET`
  - 类型/结构：`BASIC/STRUCT/ENUM`

核心接口：

```c
void lexer_init(struct lexer *lex);
struct lexer_token *lexer_scan(struct lexer *lex);
void lexer_set_input_buffer(const char *buf, size_t len);
```

扫描时先跳过空白，再按字符类别读取标识符、整数、字符串或运算符。标识符先查关键字表，没有匹配时生成 `ID`。`real_val` 字段存在于结构中，但当前词法扫描没有实现浮点数字面量。关键字表当前注册 `if/else/struct/return` 和基础类型等；词法关键字表不注册 `enum`，解析器也没有枚举声明分支，因此源语言不接受枚举声明。扫描成本随输入字符数线性增长。

### 3.2 符号与类型系统（symbols）

```c
enum type_tag {
    TYPE_INT,
    TYPE_CHAR,
    TYPE_SHORT,
    TYPE_BOOL,
    TYPE_ARRAY,
    TYPE_FUNC,
    TYPE_PTR,
    TYPE_STRUCT,
    TYPE_ENUM
};
```

类型的 `width` 用来计算局部偏移、数组占用和上下文访问宽度。数组保存元素类型与长度；指针保存所指类型；函数保存返回类型和参数类型；结构体与枚举分别保存字段表和值表。数据定义位于 `symbols.h`：
```c
struct Type {
    enum type_tag tag;
    int width;
};

struct Array {
    struct Type base;
    struct Type *of;
    int size;
};

struct PtrType {
    struct Type base;
    struct Type *to;
};

struct FuncType {
    struct Type base;
    struct Type *ret;
    struct Type **params;
    int param_count;
};

struct StructType {
    struct Type base;
    struct hashmap fields;
};

struct StructFieldInfo {
    int offset;
    struct Type *type;
};

struct EnumType {
    struct Type base;
    struct hashmap values;
};
```

作用域通过 `Env.prev` 链接：
```c
struct Env {
    struct hashmap vars;
    struct hashmap types;
    struct Env *prev;
    int level;
};
```

名称表使用链式哈希表，桶内冲突通过双向链表保存：
```c
struct list_node {
    struct list_node *next;
    struct list_node *prev;
};
```

```c
struct hashmap_entry {
    struct list_node node;
    void *key;
    void *value;
};

struct hashmap {
    struct list_node *buckets;
    uword_t bucket_count;
    int key_type;
};
```

声明通过 `env_put_var()` 或 `env_put_type()` 写入当前作用域。查找先访问当前表，未找到就沿 `prev` 向外，直到找到或到达链尾；内层声明因此可以遮蔽外层声明。结构体字段另以名称查出 `StructFieldInfo`，将字段偏移加到上下文基址。一次查找的成本取决于作用域深度及各桶的冲突长度。

### 3.3 语法分析（parser）

`struct Parser`：

```c
struct Parser {
    struct lexer       *lex;
    struct lexer_token *look;
    struct Env         *top;
    int                 used;
};
```

主要入口：

- `parser_program()`：解析整个 C 源文件（当前只支持单个 `hook()` 函数）
- `parser_block()`：`{ ... }`
- `parser_decls()`：块内局部变量声明
- `parser_stmt()`：语句（if/return/赋值/空语句/块）
- `parser_bool()/join()/rel()/expr()/term()/unary()/factor()`：表达式子层级
- `parser_offset()`：数组/结构体访问偏移计算

native 函数声明通过：

```c
extern struct hashmap native_decl_table;
void native_decl_register(const char *name, int id, int argc);
```

前端只记录 `name → (id, argc)`，不关心实现。

Native 声明记录函数名、编号与参数个数：
```c
struct NativeDecl {
    const char *name;
    int         id;
    int         argc;
};
```

解析器使用一个预读 token，按优先级递归进入表达式，使用循环处理同一级连续运算。进入块时创建 `Env`，退出时恢复父作用域。`parser_program()` 先处理顶层结构体声明，再解析 `int hook(void *ctx)`；函数外层由 `parser_block_gen()` 逐条解析语句并立即生成 IR，因此不用先保存整个函数的语法树。

`Parser.used` 按类型宽度累加，赋给每个局部变量 `Id.offset`。类型检查在构造表达式时进行；`arith_new()` 选择算术结果类型，但 `set_new()` 不检查赋值双方的类型兼容性。

## 4. AST 设计与表达能力

### 4.1 Node 基类与表达式/语句

所有 AST 节点都以 `Node` 为基类：

```c
struct Node {
    int  lexline;
    enum NodeTag tag;
    void (*gen)(struct Node *self, int b, int a);
    void (*jumping)(struct Node *self, int t, int f);
    char *(*tostring)(struct Node *self);
};
```

- `gen(self, b, a)`：生成 IR（`b/a` 为控制流标签，当前主要用于语句）
- `jumping(self, t, f)`：布尔表达式的条件跳转编码
- `tostring(self)`：调试用字符串表示

表达式基类：

```c
struct Expr {
    struct Node        base;
    struct lexer_token *op;
    struct Type        *type;
    int                 temp_no;  // 对应 IR 临时编号
};
```

语句基类：

```c
struct Stmt {
    struct Node base;
    int         after;   // 预留控制流用途
};
```

`Op` 为算术、一元和访问节点提供共同的表达式基类：
```c
struct Op {
    struct Expr base;
};
```

这些基类位于派生结构的首字段，因此生成函数可以按 `Node.tag` 转回具体节点，读取子表达式并递归处理。

### 4.2 支持的表达式节点

表达式结构把“值存在哪里”和“如何计算值”分开。变量保存偏移，常量保存数值，运算保存操作数，调用保存 Native ID 和参数：
```c
struct Constant {
    struct Expr base;
    int int_val;
};

struct Id {
    struct Expr base;
    int         offset;
    int         base_offset;
    struct StructType *st;
    int is_ctx_ptr;
};

struct Access {
    struct Op  base;
    struct Expr *array;
    struct Expr *index;
    int slot;
    int width;
};

struct CtxExpr {
    struct Expr base;
    int offset;
};

struct CtxPtrExpr {
    struct Expr base;
    int base_offset;
    struct StructType *st;
};

struct Arith {
    struct Op  base;
    struct Expr *e1;
    struct Expr *e2;
};

struct Unary {
    struct Op  base;
    struct Expr *expr;
};

struct Logical {
    struct Expr base;
    struct Expr *e1;
    struct Expr *e2;
    int temp_no;
};

struct And {
    struct Logical base;
};

struct Or {
    struct Logical base;
};

struct Not {
    struct Logical base;
};

enum AST_RelOp {
    AST_LT,
    AST_LE,
    AST_GT,
    AST_GE,
    AST_EQ,
    AST_NE,
};

struct Rel {
    struct Logical base;
    enum AST_RelOp relop;
};

struct BitAnd {
    struct Op base;
    struct Expr *e1;
    struct Expr *e2;
};

struct BitOr {
    struct Op base;
    struct Expr *e1;
    struct Expr *e2;
};

struct StringLiteral {
    struct Expr base;
    int str_id;
};

struct BuiltinCall {
    struct Expr base;
    const char *name;
    int         native_id;
    int         argc;
    struct Expr *args[4];
};
```

`Constant_true/Constant_false` 是布尔单例。`Id.offset` 表示局部变量字节偏移，`is_ctx_ptr`、`st` 和 `base_offset` 用于识别从 ctx 派生的结构体访问。`Access.slot` 与 `width` 用于计算常量下标对应的字节位置。`CtxExpr.offset` 则直接指定宿主上下文读取位置。

`Arith` 的 `+、-、*、/、%` 经 `expr_gen()` 生成 `IR_ADD/SUB/MUL/DIV/MOD`，再由 `lower_binop()` 生成 VM 算术指令。其他节点的处理路径如下：

| 运算 | 前端路径 | 指令生成路径 |
| --- | --- | --- |
| 条件中的逻辑非 `!` | `parser_unary()` → `not_new()` | `not_jumping()` 交换真假标签，再调用子表达式的 `jumping` 回调 |
| 位与 `&`、位或 `|` | `bitand_new()`、`bitor_new()` 保存两个操作数，但没有设置节点 `tag` | `expr_gen()` 没有位与、位或的分派，后端没有 `IR_AND/IR_OR` 分派；不能用它们生成位运算程序 |
| 一元负号 `-x` | `parser_unary()` → `unary_new()` → `expr_gen()` → `IR_NEG` | `ir_lower_program()` 对 `IR_NEG` 进入默认分支并调用 `abort()`，编译终止 |

`Logical` 保存两个操作数；`And/Or/Not/Rel` 通过 `jumping` 回调生成条件控制流。条件跳转与把逻辑表达式求值后存入变量是两条不同的路径。

`StringLiteral.str_id` 是字符串表索引。`BuiltinCall.args[4]` 保存参数表达式，生成时先求各参数，再发出宿主调用。

### 4.3 支持的语句节点

语句结构保存执行关系：赋值保存目标和右侧表达式，分支保存条件与子语句，顺序节点保存前后两个语句：
```c
struct Set {
    struct Stmt base;
    struct Id   *id;
    struct Expr *expr;
};

struct SetElem {
    struct Stmt base;
    struct Id   *array;
    struct Expr *index;
    struct Expr *expr;
    int slot;
    int width;
};

struct If {
    struct Stmt base;
    struct Expr *expr;
    struct Stmt *stmt;
};

struct Else {
    struct Stmt base;
    struct Expr *expr;
    struct Stmt *stmt1;
    struct Stmt *stmt2;
};

struct Seq {
    struct Stmt base;
    struct Stmt *s1;
    struct Stmt *s2;
};

struct Return {
    struct Stmt base;
    struct Expr *expr;
};
```

`Set` 在右侧求值后存入变量；`SetElem` 先计算常量下标的字节偏移再存储。`If/Else` 生成标签和条件跳转，`Seq` 按顺序生成两个子语句，`Return` 生成结果后发出 `IR_RET`。空语句由 `Stmt_Null` 表示，不生成操作指令。

## 5. IR 设计与语义

### 5.1 IR 指令集

```c
enum IR_Op {
    IR_NOP = 0,

    IR_MOVE,

    IR_ADD,
    IR_SUB,
    IR_MUL,
    IR_DIV,
    IR_MOD,

    IR_AND,
    IR_OR,

    IR_RET,
    IR_LOAD_CTX,

    IR_LOAD,

    IR_RELOP,

    IR_NEG,
    IR_NOT,

    IR_STORE,

    IR_IF_FALSE,

    IR_GOTO,

    IR_LABEL,
    IR_NATIVE_CALL,
};
```

关系运算：

```c
enum IR_RelOp { IR_GT, IR_GE, IR_EQ, IR_NE };
```

IR 结构：

```c
struct IR {
    enum IR_Op   op;

    int dst, src1, src2;      // 通用寄存槽（temp 编号）

    int array_base;           // 局部变量或数组元素的字节偏移
    int array_index;          // 逻辑偏移（当前多为 0）
    int array_width;          // 元素宽度（字节）

    enum IR_RelOp relop;      // 比较类型
    int label;                // 目标 label

    int native_id;            // native 函数 ID
    int arg_width;            // 参数宽度（当前主要用于统一 int）
    int argc;                 // 参数个数
    int args[4];              // 参数对应的 temp 编号

    struct IR *next;          // 单链表
};
```

IR 序列通过：

```c
void ir_emit(struct IR ir);
void ir_mes_get(struct ir_mes *im); // { ir_head, label_count }
```

```c
struct ir_mes {
    int label_count;
    struct IR *ir_head;
};
```

`ir_emit()` 从 `ir_region` 分配记录，用尾指针在 O(1) 时间追加到单链表。`ir_mes_get()` 扫描链表，返回表头和标签表所需大小。算术记录以 `dst/src1/src2` 连接临时值；读写记录以 `array_base` 保存已经算好的字节偏移。

这是线性的三地址风格 IR，不构造 SSA，也不运行通用优化器。`ir_lower_program()` 接受 `IR_MOVE`、`IR_ADD/SUB/MUL/DIV/MOD`、`IR_RET`、`IR_LOAD_CTX`、`IR_NATIVE_CALL`、`IR_LOAD/STORE`、`IR_IF_FALSE`、`IR_GOTO` 和 `IR_LABEL`；其他操作码进入默认分支，打印 `ir_lowering abort` 后调用 `abort()`。

## 6. AST -> IR 生成规则

### 6.1 临时变量分配

全局计数器：

```c
static int temp_count = 1;
int new_temp(void) { return temp_count++; }
```

每个 `Expr` 在首次生成时取得 `temp_no`，父表达式先分配编号，再递归生成子表达式；编号顺序因此不等于运算顺序。`dst` 和参数 `args[i]` 使用临时编号，但 `src1/src2` 的含义由操作决定，例如 `IR_MOVE.src1` 是立即数，`IR_LOAD_CTX.src1/src2` 是字节偏移与访问宽度。

### 6.2 表达式生成（expr_gen）

核心逻辑（按 tag 分派）：

- **常量** `TAG_CONSTANT`：

  ```c
  IR_MOVE: dst = int_val;
  ```

- **标识符** `TAG_ID`：

  ```c
  IR_LOAD:
      dst         = temp_no;
      array_base  = id->offset;
      array_index = 0;
      array_width = type->width;
  ```

- **数组访问** `TAG_ACCESS`（仅支持常量下标）：

  ```c
  elem_offset = slot + idx * width;
  IR_LOAD:
      dst         = temp_no;
      array_base  = elem_offset;
      array_index = 0;
      array_width = width;
  ```

- **ctx 访问** `TAG_CTX`：

  ```c
  IR_LOAD_CTX:
      dst  = temp_no;
      src1 = offset;
      src2 = type->width;
  ```

- **字符串字面量** `TAG_STRING`：

  ```c
  str_id = intern_string(unescaped);
  IR_MOVE: dst = str_id;
  ```

- **算术** `TAG_ARITH`：

  ```c
  先递归生成 e1/e2
  IR_ADD/SUB/MUL/DIV/MOD:
      dst  = temp_no;
      src1 = e1->temp_no;
      src2 = e2->temp_no;
  ```

- **一元** `TAG_UNARY`：

  ```c
  先生成 expr
  MINUS → IR_NEG: dst = -expr
  NOT   → IR_NOT: dst = !expr
  ```

上表列出 `TAG_UNARY` 分支中的 IR 对应关系。`ir_lower_program()` 对 `IR_NEG` 和 `IR_NOT` 均调用 `abort()`。源码中的 `!` 由 `parser_unary()` 创建 `Not`，在条件跳转路径中调用 `not_jumping()` 交换真假标签；它不通过 `Unary` 求值。

- **BuiltinCall / native 调用** `TAG_BUILTIN_CALL`：

  ```c
  先生成每个 args[i]
  IR_NATIVE_CALL:
      dst       = temp_no;
      native_id = b->native_id;
      argc      = b->argc;
      arg_width = type->width;
      args[i]   = args[i]->temp_no;
  ```

### 6.3 逻辑与条件跳转（jumping）

布尔表达式不直接生成“布尔值 temp”，而是通过 `jumping(t, f)` 编码为控制流：

- `And`：

  ```c
  e1.jumping(0, Lfalse);
  e2.jumping(t, f);
  ```

- `Or`：

  ```c
  e1.jumping(Ltrue, 0);
  e2.jumping(t, f);
  ```

- `Not`：

  ```c
  e1.jumping(f, t);
  ```

- `Rel`：

  - 先生成 `e1/e2` 的 temp
  - 如果 `f != 0`，生成一条 `IR_IF_FALSE`，内部用 `relop + src1/src2 + label=f`
  - 同时保留一份字符串形式 `s1 op s2`，交给 `node_emit_jumps()` 做调试输出

### 6.4 语句生成

- **return**：

  ```c
  expr_gen(expr);
  IR_RET: src1 = expr->temp_no;
  ```

- **赋值** `Set`：

  ```c
  expr_gen(expr);
  IR_STORE:
      array_base  = id->offset;
      array_index = 0;
      array_width = id->type->width;
      src1        = expr->temp_no;
  ```

- **数组元素赋值** `SetElem`（仅支持常量下标）：

  ```c
  idx = const_index;
  elem_offset = slot + idx * width;
  expr_gen(expr);
  IR_STORE:
      array_base  = elem_offset;
      array_index = 0;
      array_width = width;
      src1        = expr->temp_no;
  ```

- **顺序语句** `Seq`：

  ```c
  if s1 == Null → 只生成 s2
  if s2 == Null → 只生成 s1
  否则：
      L = newlabel();
      s1.gen(b, L);
      emit_label(L);
      s2.gen(L, a);
  ```

- **if**：

  ```c
  Lthen = newlabel();
  Lelse = newlabel();
  Lend  = newlabel();
  
  expr.jumping(0, Lelse);
  
  emit_label(Lthen);
  stmt.gen(Lthen, a);
  
  IR_GOTO Lend;
  
  emit_label(Lelse);
  emit_label(Lend);
  ```

- **if-else**：

  ```c
  Lthen = newlabel();
  Lelse = newlabel();
  Lend  = newlabel();
  
  expr.jumping(0, Lelse);
  
  emit_label(Lthen);
  stmt1.gen(Lthen, a);
  IR_GOTO Lend;
  
  emit_label(Lelse);
  stmt2.gen(Lelse, a);
  
  emit_label(Lend);
  ```

生成规则按语法树递归执行。赋值先求右值再存储，返回先求值再返回，短路条件只进入需要执行的分支。当前 if/else 转换会在已经 return 的分支后仍生成结束跳转；两侧都返回且后面没有指令时，结束标签对应的下标等于指令数量，跳转目标因此被验证器拒绝。可以在分支中赋值，在末尾统一 return。

## 7. 后端：IR → BPF 映射

### 7.1 内存布局（backend_layout）

```c
struct backend_layout {
    int temp_base;      // 临时变量起始 slot（默认 64）
    int temp_count;     // 临时变量数量（默认 64）

    int mem_a;          // 0 → mem_a（8）
    int mem_b;          // 4 → mem_b（16）
    int mem_c;          // 8 → mem_c（24）

    int mem_arr_base[4];// 12/16/20/24 → 32/40/48/56
};
```

映射函数：

```c
int temp_slot(const struct backend_layout *l, int t)
    => l->temp_base + t * 4;

int map_array_base(const struct backend_layout *l, int base)
    // 0/4/8/12/16/20/24 → mem_a/mem_b/mem_c/mem_arr_base[i]
```

临时编号通过 `temp_slot()` 转成字节偏移。当前 `ir_lower_program()` 对 `IR_LOAD/IR_STORE` 直接使用 `array_base`，它已由前端计算成字节偏移；不会统一经过 `map_array_base()`。后者用于 `selection.c` 中另列的辅助转换函数。局部区与临时区必须避免重叠，每次四字节访问也必须落在 `ccbpf_ctx.mem` 的范围内。`temp_count` 是布局字段，当前后端不会仅凭该字段限制临时值数量。

### 7.2 指令选择（selection）

指令构建器与 VM 指令的数据结构如下：
```c
struct bpf_builder {
    struct bpf_insn *insns;
    int count;
    int capacity;
};
```

```c
struct bpf_insn {
	unsigned short	code;
	unsigned char 	jt;
	unsigned char 	jf;
	long	k;
};
```

`bpf_builder_emit()` 追加一条指令并返回下标。初始容量为 128 条，满后分配两倍容量并复制旧数组，追加均摊为 O(1)。bump 区域中的旧数组直到区域销毁才回收，内存预算需要包含扩容副本。指令的 `code` 表示操作，`jt/jf` 表示条件跳转偏移，`k` 保存立即数、内存偏移或 Native ID；C `long` 的大小随 ABI 改变。

- **IR_MOVE**：

  ```c
  LD  #imm
  ST  MEM[temp_slot(dst)]
  ```

- **IR_ADD/SUB/MUL/DIV/MOD**：

  ```c
  LD   MEM[temp_slot(src1)]
  LDX  MEM[temp_slot(src2)]
  ALU{ADD/SUB/MUL/DIV} X
  // 取模对应 ALU{MOD} X
  ST   MEM[temp_slot(dst)]
  ```

- **IR_LOAD**（局部变量/数组）：

  ```c
  base_slot = array_base;
  LD  MEM[base_slot]
  ST  MEM[temp_slot(dst)]
  ```

- **IR_STORE**：

  ```c
  src_slot  = temp_slot(src1);
  base_slot = array_base;
  
  LD  MEM[src_slot]
  ST  MEM[base_slot]
  ```

- **IR_LOAD_CTX**：

  ```c
  // ctx 在 BPF VM 中作为 ABS 访问空间
  switch (width):
    1 → LD B ABS offset
    2 → LD H ABS offset
    4 → LD W ABS offset
  ST MEM[temp_slot(dst)]
  ```

- **IR_RET**：

  ```c
  LD  MEM[temp_slot(src1)]
  RET A
  ```

- **IR_NATIVE_CALL**（关键 ABI）：

  - 先求各参数，将前两个加载到 A、X，将后两个存入 `mem[0..3]`、`mem[4..7]`；暂存后两个参数之后，重新加载 A 中的参数 0。

  - 然后：

    ```c
    BPF_STMT(BPF_MISC | BPF_COP, native_id);
    ```

    触发 VM 侧的 native 分发逻辑（`native_id` 作为 COP 编号）

  - 最后：

    ```c
    ST MEM[temp_slot(dst)]
    ```

    把返回值从 A 寄存器写回 temp 槽。

- **控制流**：`IR_IF_FALSE / IR_GOTO / IR_LABEL`

  - 由 `lower_if_false / lower_goto / lower_label` 生成带 `jt/jf/k` 的 BPF 跳转
  - `patch_jumps()` 在所有 IR 降级完成后，根据 `label_pc[]` 回填跳转目标 PC

跳转回填使用 `pending` 保存尚未确定的目标：
```c
struct pending {
    int insn;
    int label;
    int is_cond;
    int true_branch;
};
```

生成标签时记录 `label_pc[label] = 当前指令数`。生成跳转时先写占位值，保存指令下标、标签和需要修补的分支。全部指令生成后，计算 `目标下标 - (跳转下标 + 1)`，写入 `jt`、`jf` 或 `k`。例如下标 5 跳到 9，偏移为 3。

指令选择与回填随 IR 和待回填数量线性增长。`patch_jumps()` 将条件跳转偏移直接转换为 `unsigned char` 后写入 `jt/jf`，不检查范围。非负偏移超过 255 时只保留低八位，例如 256 被写为 0；无条件跳转则把偏移写入 `k`。

## 8. 编译器总结

- **AST 显式建模控制流与布尔逻辑**：
  通过 `gen/jumping` 双接口，把“表达式值”和“控制流”分开编码，短路逻辑、关系运算都在 AST 层展开。
- **IR 简单、稳定、接近三地址码**：
  所有运算都围绕 `dst/src1/src2` 和“逻辑栈帧 offset”展开，方便后端做简单映射。
- **后端布局固定、可预测**：
  临时值由 `temp_slot()` 定位，局部变量和数组使用前端算出的字节偏移；ctx 通过 ABS 模式访问宿主缓冲区。
- **native 调用 ABI 明确**：
  前端记录 `native_id + argc + args temp_no`，后端按参数 ABI 选择指令，VM 按相同约定调用宿主实现。



#  ccBPF 虚拟机设计文档

## 1. 虚拟机总体结构

ccBPF 的虚拟机由三部分组成：

1. **BPF 执行器（`ccbpf_vm_step`）**：从 `ccbpf_ctx.pc` 取指，更新 A/X 和 scratch 内存，返回执行状态。
2. **程序加载器（`ccbpf_load_from_memory`）**：解析镜像、复制指令与字符串，创建程序对象。
3. **Hook 系统（`hook_register / hook_attach / hook_run`）**：按宿主事件名称查找并执行挂载程序。

加载后的程序对象保存代码、字符串和宿主上下文指针：
```c
struct ccbpf_program {
    struct bpf_insn *insns; //.text
    size_t insn_count;

    uint8_t *data;     //.data or .radata
    size_t data_size;

    uint32_t entry;

    int string_count;
    char **strings;
    void *ctx;
};
```

`ccbpf_program` 是可重复执行的程序对象；`ccbpf_ctx` 是一次执行的状态，两者分开才能暂停、恢复或从头重跑。根目录程序对象不含 `maps[]`，Map 由宿主提供并通过 Native 访问；SCP 演示使用另一种每程序 Map 布局。加载器分配的指令和字符串由 `ccbpf_unload()` 释放，宿主资源由宿主管理。

# 2. cbpf 虚拟机执行模型

执行接口接收持久的执行状态、程序、宿主数据及本次允许执行的指令数：
```c
enum ccbpf_status ccbpf_vm_step(struct ccbpf_ctx *ctx,
                                struct ccbpf_program *prog,
                                unsigned char *p,
                                unsigned int wirelen,
                                unsigned int buflen,
                                int max_insn);
```

```c
enum ccbpf_status {
    CCBPF_OK,
    CCBPF_FINISHED,
    CCBPF_MIGRATE,
    CCBPF_ERROR
};
```

执行循环每次从 `prog->insns[pc]` 取指，按 `code` 分派，修改寄存器或内存，再推进 pc。状态区分本次预算耗尽（`CCBPF_OK`）、正常返回、迁移让出和错误。继续执行必须复用同一个 `ccbpf_ctx`。

`ccbpf_run_frame()` 创建清零状态，从指令 0 开始，每次执行 64 条，直到返回或出错；遇到迁移状态也在本地继续。64 是分块步数，不是整个程序的执行上限。需要调度让出或迁移的宿主应使用 step 接口处理状态。

### 2.1 寄存器模型

VM 只有两个寄存器：

- `A`：累加器（主寄存器）
- `X`：索引寄存器

初始化：

```c
uint32_t A = 0, X = 0;
```

### 2.2 scratch 内存（mem[]）

```c
#define CCBPF_STACK_SIZE (512)

struct ccbpf_ctx {
    uint32_t A;
    uint32_t X;
    uint32_t pc;
    uint32_t ret;
    uint8_t mem[CCBPF_STACK_SIZE];
};
```

`ccbpf_ctx` 保存一次执行的完整 VM 状态：`A`、`X` 是工作寄存器，`pc` 是指令下标，`ret` 是返回值。`mem[]` 是该次执行持有的 scratch 内存，局部变量和临时计算结果按字节偏移存放其中。容量由 `ccBPF/cbpf.h` 中的 `CCBPF_STACK_SIZE` 定义；调整容量时需要同时检查编译器的内存布局和 VM 的访问边界。

scratch 区用于：

- 临时变量（temp_slot）
- 局部变量（前端计算的字节偏移）
- native 调用参数槽（mem[0], mem[4]）
- IR_LOAD / IR_STORE 映射的所有“逻辑栈帧”

从头执行程序时清零整个执行状态；分步继续时保留已有状态：

```c
struct ccbpf_ctx ctx;
memset(&ctx, 0, sizeof(ctx));
```

# 3. 指令语义

VM 沿用 classic BPF 的寄存器和指令分类，并加入 ccBPF 扩展。内存指令中的 `k` 是字节偏移，寄存器和普通存储值为四字节：

### 3.1 加载指令（LD / LDX）

- **ABS 模式**：从 frame（ctx）读取

```c
BPF_LD | BPF_W | BPF_ABS   → A = EXTRACT_LONG(&p[k])
BPF_LD | BPF_H | BPF_ABS   → A = EXTRACT_SHORT(&p[k])
BPF_LD | BPF_B | BPF_ABS   → A = p[k]
```

`EXTRACT_LONG/EXTRACT_SHORT` 通过 `memcpy` 读取四字节或两字节的原始值，不自动转换网络字节序。`p` 是宿主传入的上下文缓冲区，与保存局部值的 `ctx->mem` 分开。

- **IND 模式**：从 `p[X + k]` 读取
- **IMM 模式**：

```c
BPF_LD  | BPF_IMM → A = k
BPF_LDX | BPF_IMM → X = k
```

- **MEM 模式**：

```c
BPF_LD  | BPF_MEM → memcpy(&A, &ctx->mem[k], sizeof(uint32_t))
BPF_LDX | BPF_MEM → memcpy(&X, &ctx->mem[k], sizeof(uint32_t))
```

### 3.2 存储指令（ST / STX）

```c
BPF_ST  → memcpy(&ctx->mem[k], &A, sizeof(uint32_t))
BPF_STX → memcpy(&ctx->mem[k], &X, sizeof(uint32_t))
```

### 3.3 算术指令（ALU）

支持：

- ADD / SUB / MUL / DIV / MOD
- AND / OR
- LSH / RSH
- NEG

支持立即数和 X 寄存器两种形式。

### 3.4 跳转指令（JMP）

支持：

- 无条件跳转：`JA`
- 比较跳转：`JGT/JGE/JEQ/JSET`（支持 K 和 X）
- `jt/jf` 分支偏移

### 3.5 返回指令（RET）

```c
BPF_RET | BPF_K → return k
BPF_RET | BPF_A → return A
```

A/X 使用无符号整数语义。`RET A` 将 A 写入 `ctx->ret` 并返回 `CCBPF_FINISHED`。`bpf_validate()` 逐条执行以下检查：跳转目的下标不得大于或等于指令数量；`ST` 和 `LD MEM` 的偏移必须非负，且四字节访问不能超过 `CCBPF_STACK_SIZE`；立即数除法的除数不能为零；末条指令必须属于 `BPF_RET` 类。它不检查 `LDX MEM/STX` 的 scratch 边界，不检查无条件跳转目的的下界，也不分析循环终止性。`ccbpf_vm_step()` 对 scratch 读写和除零执行运行时检查，但取指前不检查 `pc < insn_count`。

# 4. native 调用机制（BPF_COP）

这是 ccBPF 的关键扩展。

### 4.1 IR_NATIVE_CALL → BPF_COP

后端先求参数并按 ABI 放入寄存器和参数槽，再生成 `BPF_MISC | BPF_COP`，其 `k` 保存 Native ID。运行时表以整数 ID 为键，条目保存参数数量和宿主函数：
```c
struct native_entry {
    int         func_id;
    int         argc;
    native_fn_t fn;
};
```

```c
int func_id = ins->k;
struct native_entry *e =
    hashmap_get(&native_table, (void *)(uintptr_t)func_id);
```

找到条目后，VM 按参数数量从 A、X 和 scratch 读取参数，调用 `e->fn()`，将结果放回 A；后端随后将 A 存入结果临时位置。找不到 ID 时，当前行为是把调用结果置零并继续执行。Native 是宿主 C 函数，指针、长度、资源所有权和阻塞行为需要由宿主接口约定。

### 4.2 参数 ABI

最多四个参数使用以下位置：

- `A` → a0
- `X` → a1
- `mem[0..3]` → a2
- `mem[4..7]` → a3

```c
uint32_t a0 = A;
uint32_t a1 = X;
uint32_t a2 = 0;
uint32_t a3 = 0;
if (e->argc > 2)
    memcpy(&a2, &ctx->mem[0], sizeof(uint32_t));
if (e->argc > 3)
    memcpy(&a3, &ctx->mem[4], sizeof(uint32_t));
```

暂存第三、第四个参数会覆盖 A，后端因此在发出 COP 前重新加载参数 0。VM 调用宿主函数时把当时的 A、X 作为前两个实参传入，即使声明的参数数量少于二也不清零；宿主函数只使用已声明的参数。

### 4.3 native 函数签名

```c
typedef uint32_t (*native_fn_t)(struct ccbpf_program *prog,
                                uint32_t a0, uint32_t a1,
                                uint32_t a2, uint32_t a3);
```

### 4.4 注册 native

```c
void native_register(int func_id, int argc, native_fn_t fn)
```

native 存在 `native_table`（hashmap）中。

# 5. hook 系统设计

hook 系统允许用户动态注册 hook，并 attach 多个程序。

### 5.1 hook_entry 结构

```c
struct hook_entry {
    const char *name;
    struct hook_node *head;
};

struct hook_node {
    struct ccbpf_program *prog;
    struct hook_node *next;
};
```

`hook_table` 将名称映射到 `hook_entry`，每个 entry 的 `head` 指向程序单链表。attach 在表头插入，所以新程序先执行；重复 attach 会增加节点，不会替换同名 Hook 上已有的程序。

### 5.2 注册 hook

```c
void hook_register(const char *name)
```

- 分配 `hook_entry`
- 插入 `hook_table`（hashmap）

### 5.3 attach 程序

```c
int hook_attach(const char *hook_name, uint8_t *image, size_t len)
```

流程：

1. 找到 hook_entry
2. `ccbpf_load_from_memory(image)` 加载程序
3. 插入链表头（head 插入法）
4. 程序立即生效

### 5.4 detach 程序

```c
int hook_detach(const char *hook_name)
```

- 卸载所有程序（逐个 `ccbpf_unload`）
- 清空链表

卸载沿链表逐个释放程序和节点，再清空 head，Hook 名称仍保留。替换程序时应先 detach，再 attach。

### 5.5 hook_run

```c
uint32_t hook_run(const char *hook_name, uint8_t *frame, size_t frame_size)
```

- 顺序执行链表中的所有程序
- 返回最后一个程序的返回值

Hook 执行先查名称，再沿链表顺序运行；每个程序执行前设置宿主上下文指针。空 Hook 返回零，非空 Hook 返回最后执行程序的结果，即最早挂载的程序。链表遍历与挂载数量线性相关，外加各程序执行成本。当前操作没有内部同步，并发运行与挂载/卸载需要宿主安排同步。

# 6. `.ccbpf` 文件格式

镜像由头部、指令数组和字符串表组成。头部记录各区域的字节偏移与长度：
```c
struct CCBPF_Header {
    uint32_t magic;
    uint16_t version;
    uint16_t flags;

    uint32_t code_offset;
    uint32_t code_size;

    uint32_t data_offset;
    uint32_t data_size;

    uint32_t entry;
};
```

打包器写入版本 1，入口字段为 0。指令直接按 `struct bpf_insn` 布局存储；字符串区以原生 `int` 保存数量及每个字符串的长度，然后保存含结尾零的字符串。编译端与执行端必须约定结构大小、对齐、字节序和 Native ID，镜像不能仅凭文件后缀就跨 ABI 使用。

加载流程：

1. 检查头部大小、magic 与代码区域。
2. 复制指令并调用 `bpf_validate()`。
3. 分配 `ccbpf_program`，重建字符串表。
4. 保存 entry；当前执行封装仍从指令 0 开始。

根目录加载器不创建 Map 数组。它检查镜像最小长度、magic、代码区和数据区的末端是否超过镜像长度，并调用 `bpf_validate()`。它不检查 version、flags、偏移加法溢出、代码长度是否为指令大小的整数倍，也不在调用验证器前排除空指令序列。字符串数量和长度直接从数据区读取；读取数量、长度和字符串内容前没有逐项边界检查。加载成功后程序拥有独立副本；卸载时释放指令、字符串及程序对象。

`ccbpf_pack_memory(insns, cap, count, out_len)` 返回打包区域内的指针。使用顺序是打包 → 保存或加载 → `bpf_builder_free()`；MCU 示例的三参数接口返回堆内存，使用不同的清理约定。

# 7. 程序执行流程

宿主先注册 Hook，再挂载镜像。`hook_attach()` 自己调用加载器，无需提前再加载一次：

```text
注册 Hook
    ↓ hook_attach(image)
加载与验证镜像 → ccbpf_program
    ↓ 插入 hook_node 链表
宿主事件 → hook_run(frame)
    ↓ ccbpf_run_frame
清零 ccbpf_ctx → ccbpf_vm_step
    ↓ 指令分派
更新 A/X、mem 和 pc
    ↓ RET
ctx.ret → 宿主取得返回值
```

需要逐步调度时，直接保留 `ccbpf_ctx` 并驱动 step。VM 遇到 `native_migrate` 时保存 A/X 和下一条 pc，返回 `CCBPF_MIGRATE`；`ccbpf_ctx_pack/unpack` 复制执行状态。恢复还需要兼容的程序、字符串、Native、宿主上下文及外部资源，复制状态不会让另一台设备上的地址自动有效。

# 8. 虚拟机设计总结

ccbpf 的 VM 具有以下特点：

- **沿用 classic BPF 执行模型并扩展指令**
- **scratch mem[] 作为统一的“虚拟栈帧”**
- **ctx 访问通过 ABS 模式完成**
- **native 调用通过 BPF_COP 实现**
- **hook 系统允许动态 attach/detach 程序**
- **程序加载器管理指令与字符串，Map 由宿主提供**

整个 VM 设计非常小巧、可移植、可嵌入 MCU/RTOS，也可以在 Linux 用户态运行。

# 9. 完整例子：从 C 源码到 VM 返回 8

下面的程序给 `sport` 和 `dport` 赋值，再计算 `count` 并返回。用它贯穿词法分析、语法分析、IR 生成、指令生成和虚拟机执行：

```c
int hook(void *ctx)
{
    int sport;
    int dport;
    int count;

    sport = 1;
    dport = 2;
    count = ((sport * dport) + dport) * dport;
    return count;
}
```

先手算：`1 * 2 = 2`，`2 + 2 = 4`，`4 * 2 = 8`。接下来让编译器和虚拟机完成同样的计算。

本例使用 Windows x64、MinGW 的数据布局：指针为 8 字节，`int` 和 C `long` 为 4 字节。下面的变量偏移、指令布局和镜像长度均按这一布局计算。

### 9.1 词法分析：先识别单词，暂不求值

词法分析把字符流分成 token。对于赋值语句：

```c
count = ((sport * dport) + dport) * dport;
```

识别出的顺序是：

```text
ID(count) ASSIGN LPAREN LPAREN
ID(sport) STAR ID(dport) RPAREN
PLUS ID(dport) RPAREN STAR ID(dport) SEMICOLON
```

`count`、`sport`、`dport` 都是标识符，token 保留名称；`1`、`2` 是带数值的 `NUM`；`int` 属于基本类型关键字。词法分析器还不知道 `sport` 的值是 1，也不会把三个变量都替换成 `int`。类型需要查符号表，值需要执行赋值后才确定。

对应的数据结构是 `lexer_token`：`tag` 区分 token 类别，`lexeme` 保存名称，`int_val` 保存整数值。算法在 `lexer.c` 中逐字符扫描，遇到标识符字符、数字或运算符，构造相应的 token。

调用从 `compile_and_run_example(source)` 开始：

```text
compiler_init()
  → mg_region_create_pool()       frontend_region
  → mg_region_create_bump() × 3   longterm_region / string_region / ir_region
  → init_stmt_singletons()
  → init_constant_singletons()
lexer_init(&lex) → hashmap_init() → lexer_reserve() → hashmap_put()
lexer_set_input_buffer(source, strlen(source))
parser_new(&lex)
  → hashmap_init(native_decl_table)
  → mg_region_alloc(longterm_region, sizeof(Parser))
  → env_new(NULL) → hashmap_init(vars/types) → track_hashmap()
  → parser_move() → lexer_scan()
```

`lexer_set_input_buffer()` 保存源码指针、长度，并把读位置设为 0；源码字符串在扫描结束前必须有效。`parser_move()` 把扫描结果写入 `Parser.look`。`lexer_scan()` 经 `readch()` → `reader_next_char()` 读取字符，用 `lexer.peek` 保存当前字符。标识符扫描完后调用 `hashmap_get()` 查关键字；普通名称由 `new_lexer_token_word()` 保存，整数由 `new_lexer_token_num()` 保存。扫描 `1`、`2` 时按 `v = 10 × v + digit` 累加，结果进入 `lexer_token.int_val`。单字符符号也生成 token；双字符运算符由 `readch_match()` 检查第二个字符。

每次 `parser_match()` 成功匹配都会调用 `parser_move()` 取得下一项；直接调用 `parser_move()` 的分支也执行同一扫描链。因此 `Parser.look` 始终是解析器尚未消费的那一个 token。

### 9.2 语法分析：把优先级变成树的形状

四则表达式可以用下面的文法描述；本例还需要允许标识符作为操作数：

```text
Expr   → Expr + Term | Expr - Term | Term
Term   → Term * Factor | Term / Factor | Factor
Factor → ( Expr ) | NUM | ID
```

这是表达优先级的文法。ccBPF 的递归下降解析器使用循环处理同一级连续运算，不直接对左递归规则调用自身：`parser_expr()` 处理加减，`parser_term()` 处理乘除和取模，`parser_factor()` 遇到括号时进入内部表达式。因而 `sport * dport` 先成为乘法节点，再与 `dport` 构成加法节点，最后构成外层乘法。

省去括号和 `Expr`、`Term`、`Factor` 这些文法层级后，赋值的抽象语法树是：

```text
Set(count)
└─ Mul
   ├─ Add
   │  ├─ Mul
   │  │  ├─ Id(sport)
   │  │  └─ Id(dport)
   │  └─ Id(dport)
   └─ Id(dport)
```

语法推导树包含每一层文法规则，抽象语法树只保留运算和操作数。这里的树形结构决定了计算顺序：先做内层乘法，再做加法，最后做外层乘法。

入口和函数体的调用链是：

```text
parser_program()
  → node_newlabel() × 2 → node_emitlabel(L1) → ir_emit(IR_LABEL)
  → parse_hook_function_gen()
      → parser_move()/parser_match()      消费 int hook(void *ctx)
      → ptr_new() → id_new_from_name() → id_new() → env_put_var()
      → parser_block_gen()
          → parser_match(LBRACE) → env_new(saved)
          → parser_decls()
          → parser_stmt() → 该语句的 Node.gen 回调  （逐条循环）
          → mg_region_reset(frontend_region) → parser_match(RBRACE)
  → node_emitlabel(L2) → ir_emit(IR_LABEL)
```

赋值右侧的表达式从 `parser_bool()` 开始，依次调用 `parser_join()` → `parser_bitand()` → `parser_bitor()` → `parser_rel()` → `parser_expr()` → `parser_term()` → `parser_unary()` → `parser_postfix()` → `parser_factor()`。本例没有逻辑或关系运算，外层函数直接返回下层结果。`parser_factor()` 遇到 `(` 后先调用 `parser_type()` 识别类型；这里括号内不是类型，随后调用 `parser_bool()` 解析内部表达式，再匹配 `)`。变量走名称查找路径；整数走 `constant_int()` → `constant_new()` 路径。

`parser_term()` 遇到内层 `*`，调用 `arith_new(STAR, sport, dport)`；`parser_expr()` 遇到 `+`，调用 `arith_new(PLUS, 内层乘法, dport)`；外层 `parser_term()` 再调用 `arith_new(STAR, 加法, dport)`。每次构造都将左右孩子写入 `Arith.e1/e2`，这三个调用形成上图的嵌套关系。

### 9.3 语义与符号表：名字对应什么类型、存在哪里

`parser_decls()` 为声明创建 `Id`，通过 `env_put_var()` 放入当前作用域。遇到变量使用时，解析器查找名称，取得同一个 `Id`，而不是重新创建一个只有名字的节点。

前端按类型宽度递增 `Parser.used`，为变量分配以下偏移：

| 名称 | 类型宽度 | 前端分配的偏移 | 本例中的作用 |
| --- | --- | --- | --- |
| `ctx` | 8 字节指针 | 0 | 入口参数；本例不读取上下文 |
| `sport` | 4 字节 `int` | 8 | 保存 1 |
| `dport` | 4 字节 `int` | 12 | 保存 2 |
| `count` | 4 字节 `int` | 16 | 保存运算结果 8 |

`ctx` 的偏移是前端登记参数时分配的，不表示 VM 自动把宿主指针写入暂存区。32 位构建的指针宽度不同，本例的局部变量偏移依次为 4、8、12。

类型检查与语法分析一起进行。`arith_new()` 根据左右操作数的类型选择结果类型；本例所有操作数都是 `int`，三个算术节点的结果也都是 `int`。找不到变量或算术操作数类型不受支持时，前端报错。`set_new()` 保存赋值目标和右侧表达式，不检查赋值双方的类型兼容性。

参数先在外层 `Env` 登记。`parser_block_gen()` 创建函数体的 `Env`，令其 `prev` 指向外层，三个局部变量写入函数体的 `vars` 表。声明的实际路径为：

```text
parser_decls()
  → parser_type() → basic_type_from_token() → Type_Int
  → parser_match(BASIC/ID/SEMICOLON)
  → id_new(token, Type_Int, Parser.used)
  → env_put_var() → sym_strdup() → hashmap_put()
  → Parser.used += Type_Int->width
```

登记参数后 `used = 8`；登记 `sport`、`dport`、`count` 后依次成为 12、16、20。`id_new()` 保存 `op/type/offset`，设置 `TAG_ID` 和 `expr_gen` 回调。使用变量时，`parser_factor()` 先调用 `hashmap_get(native_decl_table, name)`；本例名称均不是 Native，然后调用 `env_get_var()`。后者从当前 `Env.vars` 开始调用 `hashmap_get()`，找不到才沿 `prev` 向外查找。

`hashmap_get()` 和 `hashmap_put()` 经 `hashmap_bucket()` → `hashmap_hash()` 选桶，再遍历桶内链表、按字符串比较键；插入新条目用堆分配条目并链接到桶内。类型选择由 `arith_new()` → `type_max()` 执行：任一类型为空返回空；任一类型为 `TYPE_INT` 返回 `Type_Int`；两个都是 `TYPE_CHAR` 返回第一个；其他组合返回空，`arith_new()` 据此调用 `node_error()`。本例三个节点均返回 `Type_Int`。

### 9.4 用结构体保存这棵树

表达式节点需要保存操作符、类型和操作数；常量还需要保存数值，变量还需要保存位置。ccBPF 用以下结构表示这些信息：


| 结构 | 保存的数据 | 本例对应 |
| --- | --- | --- |
| `Node` | 节点类别和生成函数 | 决定按赋值、算术或返回处理 |
| `Expr` | 操作符、类型、`temp_no` | 每个表达式的类型及 IR 结果编号 |
| `Id` | `Expr` 和局部变量偏移 | `sport`、`dport`、`count` |
| `Constant` | `Expr` 和整数值 | 1、2 |
| `Arith` | 运算信息及 `e1`、`e2` | 两个乘法和一个加法 |
| `Set` | 目标 `Id` 和右侧表达式 | 三次赋值 |
| `Return` | 返回表达式 | `return count` |

节点保存关系，生成函数决定如何遍历关系。根目录前端逐条解析并生成函数外层语句的 IR，因此上面的树表示这一条赋值，不要求先建立整个函数的完整 AST。

赋值和返回通过 `Node.gen` 连接解析与 IR 生成：

```text
parser_block_gen() → parser_stmt()
  赋值：→ parser_assign() → env_get_var() → parser_bool() → set_new()
        → s->base.gen(...) → set_gen() → expr_gen(rhs) → ir_emit(IR_STORE)
  返回：→ parser_bool() → return_new()
        → s->base.gen(...) → return_gen() → expr_gen(count) → ir_emit(IR_RET)
```

`Set.id` 指向赋值目标，`Set.expr` 指向右侧树，`Set` 的 `Node.tag = TAG_SET`、`Node.gen = set_gen`。三个 `Arith` 的 `Expr.op` 分别为 `STAR/PLUS/STAR`，`Expr.type = Type_Int`，`Node.tag = TAG_ARITH`，生成回调是 `expr_gen`。`Return.expr` 指向符号表中的 `count` 节点，生成回调是 `return_gen`。这些节点通过 `mg_region_alloc(longterm_region, sizeof(...))` 分配，函数体内的 `mg_region_reset(frontend_region)` 不释放它们。

`set_gen()` 发出存储记录后还调用左右节点的 `tostring` 回调和 `node_emit()`。本例会经过 `id_tostring()`、`constant_tostring()`、`arith_tostring()`，再通过 `token_to_string()`、`region_strdup()` 构造文字；这些是文本表示，不是额外的 IR 运算。

### 9.5 IR：把嵌套计算拆成加载、运算和存储

`expr_gen()` 先给表达式分配结果编号，再递归生成操作数，最后发出本节点的运算。`set_gen()` 在右侧表达式完成后发出 `IR_STORE`；`return_gen()` 生成返回表达式后发出 `IR_RET`。

生成的 IR 如下。`t1` 至 `t8` 是表达式结果的临时编号；`mem[n]` 表示从暂存区的字节偏移 n 处读写一个四字节整数：

```text
LABEL L1
MOVE  t1 <- 1
STORE mem[8] <- t1
MOVE  t2 <- 2
STORE mem[12] <- t2
LOAD  t6 <- mem[8]
LOAD  t7 <- mem[12]
MUL   t5 <- t6 * t7
LOAD  t7 <- mem[12]
ADD   t4 <- t5 + t7
LOAD  t7 <- mem[12]
MUL   t3 <- t4 * t7
STORE mem[16] <- t3
LOAD  t8 <- mem[16]
RET   t8
LABEL L2
```

为什么外层结果是 `t3`，内部乘法却是 `t5`？生成器先为外层乘法分配 `t3`，再为加法分配 `t4`、内层乘法分配 `t5`，随后才访问变量。这是编号分配顺序；指令的执行顺序仍是先内层、后外层。

为什么 `t7` 被加载三次？同一作用域中的三个 `dport` 引用指向同一个 `Id`，第一次生成时给它分配 `temp_no = 7`，之后复用该编号。每次引用仍发出一次 `LOAD`，当前生成器不会把重复读取消除。最后单独读取 `count`，把它放入 `t8` 后返回。

IR 是通过 `next` 串联的记录链表，赋值目标和读取源使用 `array_base` 保存局部偏移。调试输出中的 `MEM[8 + t0 * 4]` 在这里表示下标字段为 0，实际地址就是偏移 8；它不表示执行时还要读取一个 `t0`。

以 `count` 的赋值为例，递归调用和输出顺序分别如下：

| `expr_gen()` 当前节点 | 对结构体的操作 | 递归返回后发出的 IR 字段 |
| --- | --- | --- |
| 外层 `Arith(STAR)` | `new_temp()` → `temp_no = 3`；递归 `e1`、`e2` | `op=MUL, dst=3, src1=4, src2=7` |
| `Arith(PLUS)` | 分配 `temp_no = 4`；递归两个孩子 | `op=ADD, dst=4, src1=5, src2=7` |
| 内层 `Arith(STAR)` | 分配 `temp_no = 5`；递归两个孩子 | `op=MUL, dst=5, src1=6, src2=7` |
| `Id(sport)` | 首次分配 `temp_no = 6`，读取 `offset=8` | `op=LOAD, dst=6, array_base=8, array_index=0, array_width=4` |
| `Id(dport)`，共三次访问 | 首次分配 `temp_no = 7`，以后复用；每次读取 `offset=12` | 每次均为 `op=LOAD, dst=7, array_base=12, array_index=0, array_width=4` |
| 回到 `Set(count)` | 读取 `id->offset=16` 和 `expr->temp_no=3` | `op=STORE, src1=3, array_base=16, array_index=0, array_width=4` |

编号在进入节点时分配，运算记录在孩子生成完成后追加，因而编号是先序、运算输出是后序。前两次赋值已分别经过 `constant_int()` → `constant_new()` → `expr_gen()`，生成 `IR_MOVE(dst=1,src1=1)` 和 `IR_MOVE(dst=2,src1=2)`，再由 `set_gen()` 存到偏移 8、12。返回时 `return_gen()` → `expr_gen(Id(count))` 分配 `t8`、发出 `IR_LOAD`，然后发出 `IR_RET(src1=8)`。

所有记录进入 `ir_emit()`：在 `ir_region` 分配 `IR`，复制字段，令新记录 `next=NULL`；链表非空时写 `ir_tail->next`，否则写 `ir_head`，最后更新 `ir_tail`。本例共有 16 条记录，其中两条是标签。每条语句的 IR 完成后，解析器继续读取下一条语句；结束标签追加后，`frontend_destroy()` → `hashmap_destroy()`、`symbol_destroy()`、`mg_region_destroy()` 释放词法表、作用域表及前端两类区域，IR 链表仍由 `ir_region` 保存。

### 9.6 后端：给临时值安排位置，选择 VM 指令

VM 只有 A、X 两个工作寄存器，临时值需要存入暂存区。`temp_slot()` 按 `64 + 4 × 临时值编号` 计算位置：

| 临时值 | 字节偏移 | 最终值 | 含义 |
| --- | --- | --- | --- |
| `t1` | 68 | 1 | 第一次赋值的常量 |
| `t2` | 72 | 2 | 第二次赋值的常量 |
| `t3` | 76 | 8 | 外层乘法结果 |
| `t4` | 80 | 4 | 加法结果 |
| `t5` | 84 | 2 | 内层乘法结果 |
| `t6` | 88 | 1 | 读取的 `sport` |
| `t7` | 92 | 2 | 读取的 `dport` |
| `t8` | 96 | 8 | 读取的 `count` |

`ir_lower_program()` 顺着链表选择指令：立即数加载后存入临时位置；局部读取和赋值各用一次加载、一次存储；二元运算先把两个临时值分别读入 A、X，运算后再存回结果位置。

例如 `MUL t5 <- t6 * t7` 变为：

```text
LD  mem[88]     A = t6
LDX mem[92]     X = t7
MUL X          A = A * X
ST  mem[84]     t5 = A
```

全程序生成 **34 条指令**：两次常量赋值各 4 条，四次变量读取共 8 条，三个二元运算共 12 条，写入 `count` 2 条，返回 2 条。两个标签只记录位置，不生成指令；没有分支，因此没有跳转需要回填。下方执行表列出完整指令序列。

后端调用链及数据转换为：

```text
bpf_builder_init() → mg_region_create_bump() → mg_region_alloc()
ir_mes_get() → 遍历 IR.next，得到 ir_head 和 label_count=3
ir_lower_program() → default_bpf_layout() → 分配 pending[] / label_pc[]
  IR_LABEL → lower_label() → label_pc[label] = builder.count
  IR_MOVE  → lower_move()  → temp_slot() → bpf_builder_emit() × 2
  IR_LOAD/STORE → temp_slot() → bpf_builder_emit() × 2
  IR_MUL/ADD → lower_binop() → temp_slot() × 3 → bpf_builder_emit() × 4
  IR_RET → temp_slot() → bpf_builder_emit() × 2
  → patch_jumps()
ir_free() → mg_region_destroy(ir_region)
```

`bpf_builder` 起始 `count=0, capacity=128`，`insns` 指向后端区域中的数组。`bpf_builder_emit()` 把一条 `bpf_insn` 写入 `insns[count]` 后递增 `count`；本例只有 34 条，不调用 `bpf_builder_grow()`。`default_bpf_layout()` 的 `temp_base=64`，`temp_slot()` 把 IR 临时编号变成字节偏移。标签 L1、L2 分别写入 `label_pc[1]=0`、`label_pc[2]=34`；`pending` 数量为 0，`patch_jumps()` 不改指令。

| IR 记录（按输出顺序） | 选择路径 | 写入的指令下标 |
| --- | --- | --- |
| `LABEL L1` | `lower_label()` | 无指令，记录 0 |
| `MOVE t1; STORE mem[8]` | `lower_move()`；STORE 分支 | 0–1；2–3 |
| `MOVE t2; STORE mem[12]` | `lower_move()`；STORE 分支 | 4–5；6–7 |
| `LOAD t6; LOAD t7; MUL t5` | LOAD 分支；`lower_binop()` | 8–9；10–11；12–15 |
| `LOAD t7; ADD t4` | LOAD 分支；`lower_binop()` | 16–17；18–21 |
| `LOAD t7; MUL t3` | LOAD 分支；`lower_binop()` | 22–23；24–27 |
| `STORE mem[16]; LOAD t8; RET t8` | STORE、LOAD、RET 分支 | 28–29；30–31；32–33 |
| `LABEL L2` | `lower_label()` | 无指令，记录 34 |

### 9.7 打包与加载：指令数组变成可执行程序对象

镜像头中的 `version` 和 `flags` 与代码、字符串的偏移一起保存。



`ccbpf_pack_memory()` 写入头部、34 条指令和字符串表。按本例的数据布局，头部为 28 字节，每条指令为 8 字节；程序没有字符串，数据区仍保存一个四字节的字符串数量 0：

```text
0..27       CCBPF_Header
28..299     34 × 8 字节指令
300..303    字符串数量 0
总长度      304 字节
```

头部的 `code_offset = 28`、`code_size = 272`、`data_offset = 300`、`data_size = 4`、`entry = 0`。这 304 字节是镜像文件长度，不是编译器或 VM 的 RAM 用量。

加载器检查镜像头和代码区域，复制指令并调用 `bpf_validate()`，再创建 `ccbpf_program`。本例的暂存区访问和指令序列通过验证。成功加载后，程序拥有自己的指令副本，原打包区可以释放；在加载之前释放 builder 则会使镜像指针失效。

`bpf_builder_data()` 返回指令数组指针，`bpf_builder_count()` 返回 34；二者传入 `ccbpf_pack_memory()`。打包器调用 `mg_region_create_bump()` 和 `mg_region_alloc()` 得到镜像区域，以 `memcpy()` 写头部、指令数组和字符串数量，并通过 `out_len` 写回 304。

加载路径为 `ccbpf_load_from_memory(image, 304)` → 检查头部和代码区 → 堆分配并复制 272 字节指令 → `bpf_validate(insns,34)` → 堆分配并清零 `ccbpf_program` → 读取字符串表 → 返回程序指针。本例没有跳转；所有 `ST` 和 `LD MEM` 访问均在 scratch 边界内，末条为 `RET A`，验证返回 1。随后设置 `prog.insns`、`insn_count=34`、`string_count=0`、`entry=0`；不分配任何字符串内容。

`bpf_builder_free()` 清空 builder 字段，再依次销毁 `string_region`、`backend_region` 和 `pack_region`。此时镜像和 builder 指针失效，而 `prog.insns` 是加载器复制出的独立指令数组，仍可执行。

### 9.8 VM 执行：逐条更新 A、X 和暂存区

执行开始时 `ccbpf_ctx` 清零，`pc = 0`、`A = 0`、`X = 0`。为了看清每一步，这里每次调用 `ccbpf_vm_step()` 只执行一条指令，并复用同一个执行状态。

下面的 `pc` 是被执行指令的下标，A、X 是该条指令执行后的值。`LD` 与 `ST` 读写四字节；`jt`、`jf` 在本程序中全部为 0，表内省略。

第 14 条指令得到 2，第 20 条得到 4，第 26 条得到 8。第 29 条把 8 写入 `count`，第 33 条 `BPF_RET | BPF_A` 将 A 写入 `state.ret`，返回 `CCBPF_FINISHED`。返回指令不会再递增 pc，因此结束状态中的 pc 仍是 33。

这就完成了最初的计算：源码中的名字变成符号表条目，表达式树变成 IR，IR 变成指令，指令改变寄存器和暂存区，最终由 VM 返回 8。

每次调用都走同一个取指循环：`compile_and_run_example()` → `ccbpf_vm_step(&state,prog,NULL,0,0,1)` → 从 `state` 取出 `A/X/pc` → 读取 `prog->insns[pc]` → 按 `bpf_insn.code` 分派。立即数加载把 `k` 写入 A；`LD MEM/LDX MEM` 检查 `k` 对应的四字节范围后用 `memcpy()` 读入 A/X；`ST` 检查范围后将 A 复制到 `state.mem+k`。`MUL X`、`ADD X` 直接更新 A。

普通指令结束后递增局部 pc；一条指令预算用完，函数把 A/X/pc 写回 `state` 并返回 `CCBPF_OK`，宿主循环再次调用。第 33 条走 `BPF_RET|BPF_A` 分支，将 A 写入 `state.ret`，保存 A/X/pc 并立即返回 `CCBPF_FINISHED`。宿主据此退出循环，检查 `ret==8`。这条路径没有调用 `ccbpf_vm_run()`，也没有创建第二个执行状态。

### 9.9 用宿主接口把整个过程串起来

把本节开头的程序作为源码字符串传给 `compile_and_run_example()`，它会完成编译、加载和逐条执行，并打印每一步的寄存器状态。返回 0 表示 VM 执行结束且结果为 8。示例中的池容量可根据宿主的内存预算和程序规模调整。

```c
#include <stdio.h>
#include <string.h>
#include "lexer.h"
#include "parser.h"
#include "ir.h"
#include "ir_lowering.h"
#include "bpf_builder.h"
#include "ccbpf.h"

int compile_and_run_example(const char *source)
{
    struct lexer lex;
    struct bpf_builder builder;
    struct ir_mes ir;
    size_t image_len = 0;

    compiler_init(16, 30 * 1024, 1024, 15 * 1024);
    lexer_init(&lex);
    lexer_set_input_buffer(source, strlen(source));
    struct Parser *parser = parser_new(&lex);
    parser_program(parser);
    frontend_destroy(&lex);

    bpf_builder_init(&builder, 24 * 1024);
    ir_mes_get(&ir);
    ir_lower_program(ir.ir_head, ir.label_count, &builder);
    ir_free();

    uint8_t *image = ccbpf_pack_memory(
        bpf_builder_data(&builder), 7 * 1024,
        (size_t)bpf_builder_count(&builder), &image_len);
    struct ccbpf_program *prog = image
        ? ccbpf_load_from_memory(image, image_len) : NULL;
    bpf_builder_free(&builder);
    if (!prog)
        return -1;

    struct ccbpf_ctx state = {0};
    enum ccbpf_status status;
    do {
        uint32_t pc = state.pc;
        status = ccbpf_vm_step(&state, prog, NULL, 0, 0, 1);
        printf("pc=%u A=%u X=%u ret=%u status=%d\n",
               pc, state.A, state.X, state.ret, status);
    } while (status == CCBPF_OK);

    int ok = status == CCBPF_FINISHED && state.ret == 8;
    ccbpf_unload(prog);
    return ok ? 0 : -1;
}
```

本程序不读取 `ctx`，也不调用 Native，因此逐步执行时不需要上下文缓冲区或注册宿主函数。若只关心最终结果，可以调用 `ccbpf_run_frame(prog, NULL, 0)`，得到 8。也可以把同一镜像挂载到宿主注册的 Hook，再通过 `hook_run()` 执行。

结果检查后，`compile_and_run_example()` → `ccbpf_unload(prog)` 释放指令副本、可选数据、逐条字符串、字符串指针表和 `ccbpf_program`；`state`、`lex`、`builder`、`ir` 是宿主函数的局部对象，在函数返回时结束生命周期。区域分配通过 `mg_region_alloc()` 分派到 pool 或 bump：bump 按四字节对齐并推进 `offset`；pool 选择块大小并通过 `membit_alloc()` 取块。`mg_region_destroy()` 分别释放 bump 缓冲区，或调用 `membit_destroy()` 释放 pool 及其节点。

同一程序还有两条宿主执行入口：

```text
只取结果：ccbpf_run_frame() → 清零 ccbpf_ctx
         → 循环 ccbpf_vm_step(...,64) → FINISHED 时返回 ctx.ret

动态挂载：ccbpf_system_init() → 初始化 Hook / Native 名称表
         hook_register() → 创建 hook_entry → hashmap_put()
         hook_attach() → find_hook() → ccbpf_load_from_memory()
                       → 创建 hook_node，插入 hook_entry.head
         hook_run() → find_hook() → 遍历 hook_node.next
                    → 设置 prog.ctx → ccbpf_run_frame() → ccbpf_vm_step()
         hook_detach() → find_hook() → ccbpf_unload() → 释放 hook_node
```

直接执行返回 8；挂载执行也经过相同的 34 条指令返回 8。挂载链表和程序指令由宿主持有，执行状态由每次 `ccbpf_run_frame()` 调用持有，二者的生命周期不同。
