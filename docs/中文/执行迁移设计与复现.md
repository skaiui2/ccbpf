# ccBPF 执行迁移：设计、实现与复现

[English](../English/execution-migration.md) · [系统论文](../papers/ccBPF-Compiler-Runtime-and-Migration.pdf)

## 摘要

执行迁移让一段已经开始运行的程序换一个设备继续执行。ccBPF 将程序编译成字节码，把运行位置、工作寄存器、局部变量和中间结果保存在 VM 状态中。程序调用 `migrate()` 后，虚拟机完成该宿主函数调用，保存下一条指令的位置并把控制权交还宿主；宿主传送程序镜像和状态，目标节点重新加载镜像、恢复状态，从保存的位置继续执行。

本文沿着数据结构和算法说明这一过程，并整理两条集成路径：仓库中的 nodeC → nodeD 主机演示，以及 LTTit 中 Pico 2W → STM32F103C8T6 的硬件演示。配套复现程序使用仓库原有 `migrate.bpf` 和当前编译器、VM，核验快照恢复及迁移前后执行的连续性。本次 Windows x64、MinGW GCC 13.1.0、`-Os` 验证得到 200 条指令、1,695 字节镜像、528 字节快照；恢复位置为 87，迁移后的输出接着从 6 到 11，最终状态与同节点基线完全一致，返回 0。扩展实验还完成 7,518 次检查点恢复、两种优化下的主机微基准和十次新进程交接；板间端到端迁移耗时、MCU 峰值内存与故障恢复没有新增测量。

## 1. 迁移解决什么问题

动态加载解决“运行什么程序”，执行迁移解决“已运行的程序在哪里继续”。只发送源码或镜像，目标节点只能从头开始；仅保存变量也不够，因为还要恢复当前指令和没有写回变量的中间结果。直接复制 CPU 的机器栈，则涉及指令集、调用约定和地址布局。

ccBPF 将计算放在 VM 的执行状态中。目标节点执行相同的字节码语义，恢复这个状态就能接着执行，不需要搬运原 CPU 的机器栈。宿主的文件、设备、网络连接和外部数据仍需要另外安排。

现有演示由源码中的 `migrate()` 主动请求迁移。`ccbpf_vm_step()` 也在执行预算耗尽时保存指令边界状态，但 nodeC/nodeD 没有实现自动迁移调度。这里讨论的是协作式的 VM 执行迁移。

### 1.1 相关工作与本文定位

传感器网络已有 Maté 虚拟机和 Agilla 移动代理等研究。Maté 由 Levis、Culler 于 ASPLOS 2002 发表；Agilla 支持代理在传感器网络中迁移并通过元组空间协调，见 Fok、Roman、Lu 的 IPSN/SPOTS 2005 论文。受限设备上的执行移动并非 ccBPF 首创。

本文关注 C 子集编译器、classic-BPF 风格状态机、Native 调用后的恢复边界和两种宿主集成的具体实现，以实际指令轨迹检查和新进程恢复给出证据。没有运行 Maté 或 Agilla 的性能对照，因此不主张相对它们的内存、速度或可靠性优势。完整引文见英文论文的相关工作和参考资料。

| --- | --- | --- | --- |

## 3. 数据结构：迁移时保留什么

### 3.1 VM 状态

`ccBPF/cbpf.h` 中的定义为：

```c
#define CCBPF_STACK_SIZE (512)

struct ccbpf_ctx {
    uint32_t A;
    uint32_t X;
    uint32_t pc;
    uint32_t ret;
    uint8_t  mem[CCBPF_STACK_SIZE];
};
```

| 字段 | 保存的内容 | 恢复时的作用 |
| --- | --- | --- |
| `A/X` | 工作寄存器 | 继续尚未写回 scratch 的运算或函数结果 |
| `pc` | 让出执行时的下一条指令下标 | 指定目标节点的取指位置 |
| `ret` | 返回值 | 保留 VM 返回状态中的值 |
| `mem` | 局部变量、临时值及 Native 参数暂存 | 保留计算数据 |

这份状态没有 C 指针字段。`CCBPF_STACK_SIZE` 是构建配置，可按需求调整；编译器布局、发送端和接收端必须使用兼容配置。容量记作 B 时，状态包含四个 32 位字段和 B 字节工作内存，大小为 B+16 字节，再计入 ABI 填充。本次实验配置 B=512，`sizeof(ccbpf_ctx)=528`。迁移要复制整个数组；只复制变量 `a` 会丢掉编译器安排的临时值。528 字节是状态大小，不是迁移过程的总 RAM 占用。

### 3.2 程序镜像和运行对象

```c
struct bpf_insn {
    unsigned short code;
    unsigned char jt;
    unsigned char jf;
    long k;
};

struct ccbpf_program {
    struct bpf_insn *insns;
    size_t insn_count;
    uint8_t *data;
    size_t data_size;
    uint32_t entry;
    int string_count;
    char **strings;
    void *ctx;
};
```

镜像保存指令和程序引用的字符串。目标端调用 `ccbpf_load_from_memory()`，创建本地 `ccbpf_program`，分配并复制指令及字符串。结构中的指针不能直接从源端复制到目标端；目标端需要重新建立这些运行对象。卸载由 `ccbpf_unload()` 释放它们。

快照不包含镜像、Native 注册表、宿主输入缓冲区、`prog.ctx` 指向的数据、Map、文件句柄或设备状态。本例只有局部算术和打印函数，迁移包中的镜像与 VM 状态足以保留这段计算；使用外部可变状态的程序需要单独恢复其依赖。

### 3.3 Native 绑定

```c
typedef uint32_t (*native_fn_t)(struct ccbpf_program *p,
                              uint32_t a0, uint32_t a1,
                              uint32_t a2, uint32_t a3);

struct native_entry {
    int func_id;
    int argc;
    native_fn_t fn;
};
```

编译器把函数名转换成 Native ID，VM 再用 ID 查出本机函数。演示中 `print=3`、`print_str=4`、`migrate=8`。目标节点重新注册本机实现，传输包里不携带源节点的函数地址。两端必须约定同一 ID 的参数和语义。

## 4. 算法：从源码调用到 VM 暂停

### 4.1 编译 `migrate()`

nodeC 的 `native_init_frontend()` 调用 `native_decl_register("migrate",8,0)`，把 `NativeDecl` 放进 `native_decl_table`。随后执行：

```text
compile_to_image()
  → compiler_init() → lexer_init() → lexer_set_input_buffer()
  → parser_new() → native_init_frontend() → parser_program()
      → parser_block_gen() → parser_stmt()
      → parser_bool() → parser_join() → parser_bitand() → parser_bitor()
      → parser_rel() → parser_expr() → parser_term() → parser_unary()
      → parser_postfix() → parser_factor()
      → hashmap_get(native_decl_table, "migrate")
      → builtin_call_new(name, native_id=8, argc=0, args)
      → Node.gen / expr_gen(TAG_BUILTIN_CALL)
      → ir_emit(IR_NATIVE_CALL)
  → frontend_destroy()
  → bpf_builder_init() → ir_mes_get() → ir_lower_program()
      → IR_NATIVE_CALL 分支 → temp_slot() → bpf_builder_emit()
  → ir_free() → ccbpf_pack_memory()
```

`BuiltinCall` 保存 Native ID、参数表达式、参数数量和结果临时编号。`expr_gen()` 先生成参数表达式，再发出 `IR_NATIVE_CALL`。后端把参数 0 放到 A、参数 1 放到 X，参数 2、3 写入 scratch 偏移 0、4；有参数时最后重新加载参数 0。随后发出 `COP native_id`，再把返回值 A 存入结果临时位置。

完整的表达式下降路径是 `parser_bool()` → `parser_join()` → `parser_bitand()` → `parser_bitor()` → `parser_rel()` → `parser_expr()` → `parser_term()` → `parser_unary()` → `parser_postfix()` → `parser_factor()`。无参数的 `migrate()` 直接构造调用节点；声明查找和指令生成没有另一套迁移专用解析器。

本次 `migrate.bpf` 编译中，调用对应：

```text
IR_NATIVE_CALL: native_id=8, argc=0, dst=20
86: COP 8
87: ST mem[144]    // 64 + 4 × t20
```

第 87 条仍然属于这次调用的结果存储。因此恢复位置应是 87，不能跳到下一个源码打印语句，也不能重跑第 86 条。

### 4.2 VM 保存下一条指令

`native_migrate()` 本身只返回 0，不负责序列化或传输。迁移让出由 `ccbpf_vm_step()` 的 COP 分支完成：

```c
A = e->fn(prog, a0, a1, a2, a3);

if (e->fn == native_migrate) {
    ctx->A = A;
    ctx->X = X;
    ctx->pc = pc + 1;
    return CCBPF_MIGRATE;
}
```

具体顺序是读取 `ins->k` → `hashmap_get(native_table,id)` → 调用登记的 `fn` → 把返回值写入 A → 比较函数指针 → 保存 A/X 和 `pc+1` → 返回迁移状态。检测条件是 `fn==native_migrate`，不是硬编码的 ID 8。没有注册对应函数时，COP 将 A 设为 0 并继续；把 ID 8 注册成其他函数也不会触发这条迁移路径。

返回迁移状态前，宿主函数已经调用完毕，scratch 留在 `ctx.mem` 中。本例 A=0、X=1、pc=87；目标 VM 从结果存储开始执行，使用恢复的 A 写入 `mem[144]`。这解释了为什么保存寄存器与保存局部变量同样必要。

### 4.3 宿主处理执行状态

| 状态 | 含义 | 宿主动作 |
| --- | --- | --- |
| `CCBPF_OK` | 本次指令预算耗尽，状态已保存 | 复用同一个状态继续，或让出调度 |
| `CCBPF_FINISHED` | 执行 RET，返回值进入 `ctx.ret` | 记录结果并结束 |
| `CCBPF_MIGRATE` | 完成迁移 Native 后暂停 | 停止源端执行，打包并传送 |
| `CCBPF_ERROR` | VM 进入错误路径 | 停止并报告 |

演示每次执行 64 条，这是一次调用的预算，不是全程序执行上限。迁移驱动必须使用 `ccbpf_vm_step()` 并保留 `ccbpf_ctx`。`ccbpf_run_frame()` 会新建清零状态，并在遇到迁移状态后继续本地执行；用它接收已经恢复的状态会重新开始程序。

## 5. 快照打包、恢复与连续性

`ccbpf_ctx_pack()` 设置输出长度为 `sizeof(*ctx)`，用 `heap_malloc()` 分配缓冲区，再 `memcpy()` 整个状态；成功返回 0，分配失败返回 -1。调用方负责 `heap_free()`。

`ccbpf_ctx_unpack()` 首先比较长度；不等于 `sizeof(*ctx)` 就返回 -1，目标状态不被修改。长度相等时复制数据并返回 0。它不检查 `pc` 是否属于程序，也不检查快照与镜像是否配对。

这是一份 C 结构体的原生内存拷贝，没有统一字节序、版本字段或架构转换。状态打包成本随状态大小线性增长；加载和传输镜像再增加镜像长度。迁移峰值内存还包含已经加载的程序、发送缓冲区、接收缓冲区及分配器开销。

连续性所需的条件是：恢复后的 `(A,X,pc,ret,mem)` 与暂停状态相同，目标执行同一字节码语义，后续输入和 Native 返回结果与基线一致。在这些条件下，下一步取到相同指令、使用相同状态；沿后续步骤重复这一推理，可得到相同 VM 状态序列。这是有前提的执行模型推理，不是对整个解释器或外部副作用的形式化验证。

## 6. 主机 demo 的实现

### 6.1 调用链和协议

```text
nodeD main() → recv_from_nodeC() → socket/bind/listen/accept
nodeC main() → compile_to_image() → ccbpf_load_from_memory()
             → ccbpf_vm_step() → CCBPF_MIGRATE
             → ccbpf_ctx_pack() → send_to_nodeD() → socket/connect/write
nodeD recv_from_nodeC() → read 镜像与快照
      → ccbpf_system_init() → native_register_all()
      → ccbpf_load_from_memory() → ccbpf_ctx_unpack()
      → ccbpf_vm_step() → CCBPF_FINISHED
```

传输使用同机 Unix-domain stream socket，路径 `/tmp/ccbpf_migrate.sock`，格式依次为：

```text
原生 size_t 镜像长度 | 镜像 | 原生 size_t 状态长度 | 状态
```

发送和接收都直接调用单次 `write/read`，没有处理短写、短读、长度上限、确认和重试。流式 socket 不保证一次读取获得完整应用层消息；这个演示协议不能直接作为跨设备协议使用。

### 6.2 镜像的生命周期

当前 root 实现的 `ccbpf_pack_memory()` 返回 `pack_region` 内的指针。nodeC 的 `compile_to_image()` 调用 `bpf_builder_free()` 时销毁这个区域，却继续返回镜像指针；之后的 `heap_free(img)` 也与区域分配不匹配。这是明确的对象生命周期错误，不能据此否定原来的演示记录，但当前复现需要保留有效镜像。

配套 `migration_reproduce.c` 在释放 builder 前，将镜像复制到独立拥有的缓冲区，再用于源端加载和目标端加载。原 demo 源文件保持不变。LTTit 的镜像打包器使用不同的堆分配实现，不存在这个相同的 pack-region 释放顺序，不能混用两套 API。

Linux 下原 demo 的启动顺序如下；验证当前 VM 连续性请优先使用下一节的独立复现程序：

```bash
# 终端一，仓库根目录
cmake -S nodeD -B /tmp/ccbpf-nodeD
cmake --build /tmp/ccbpf-nodeD
/tmp/ccbpf-nodeD/nodeD

# 终端二，仓库根目录
cmake -S nodeC -B /tmp/ccbpf-nodeC
cmake --build /tmp/ccbpf-nodeC
/tmp/ccbpf-nodeC/nodeC "$PWD/migrate.bpf"
```

nodeC/nodeD 的 CMake 文件固定 Debug 和 `-O0`，打印函数还带一秒等待。这些设置服务于观察演示，不能用来报告优化构建的迁移性能。Unix-domain socket 源码需要 POSIX 环境，不能直接用 Windows 原生工具链编译。

## 7. LTTit 硬件集成

### 7.1 从 Shell 到 STM32

Pico 通过文件系统保存程序，通过 Shell 编译和运行。迁移发送任务与执行程序的任务通过信号量交接：

```text
Pico shell_main() → semaphore_create() → task_create(task_migrate_sender,...)
cmd_compile() → load_text_file_heap_fs() → parser_program()
              → ir_lower_program() → ccbpf_pack_memory() → fs_write()/fs_sync()
cmd_runbpf() → fs_open()/fs_read() → ccbpf_load_from_memory()
             → 清零 g_ctx → ccbpf_vm_step()
             → CCBPF_MIGRATE → semaphore_release(sem_migrate)
task_migrate_sender() → semaphore_take() → ccbpf_ctx_pack()
                      → 组装镜像和状态
                      → rpc_call(RPC_OP_WRITE, "/root/nodeB/vm/migrate")
```

RPC 和接收端继续执行：

```text
rpc_call() → encode_request_tlv() → rpc_send_message()
           → transport / SCP / UART
rpc_on_data() → rpc_dispatch_message() → rpc_handle_request()
             → world 的 RPC_OP_WRITE 分派 → file_ops.write
vm_migrate_register() → world_register("root/nodeB/vm/migrate",...)
vm_migrate_write() → 检查负载长度 → 复制镜像和状态
                   → ccbpf_load_from_memory() → ccbpf_ctx_unpack()
                   → ccbpf_vm_step() → STM32 打印结果
```

`/root/nodeB/vm/migrate` 指向目标端接收处理函数。请求的数据部分是：

```text
uint32_t 镜像长度 | uint32_t 状态长度 | 镜像 | 状态
```

这些字段使用原生表示；数据部分大小为 `8 + image_len + ctx_len`，之后才是 RPC/SCP/UART 的封装开销。它与主机 demo 的 `size_t` 流格式不同。

LTTit 的 `ccbpf_pack_memory(insns,count,out_len)` 用 `heap_malloc()` 分配镜像，`bpf_builder_free()` 不释放镜像。root 的打包函数另有容量参数，并使用 pack region；移植时应遵循各自的分配和释放关系。

源代码位置为 LTTit 的 `lttit/shell/source/shell.c`、`test/blink.c`、`test1/Core/Src/main.c`、`lttit/world/source/world.c` 和 `lttit/CSC/ccrpc/source/rpc.c`。恢复机制相同，传输和宿主资源由 LTTit 提供。

### 7.2 硬件复现路线

原硬件演示程序如下，返回 1129，与 root 的计数 demo 分开使用：

```c
int hook(void *ctx)
{
    int a;
    a = 1; print(a);
    a = a + 1; print(a);
    a = a + 1; print(a);
    a = a + 1; print(a);
    migrate();
    a = a + 1; print(a);
    a = a + 1; print(a);
    a = a + 1123; print(a);
    return a;
}
```

Pico 固件工程为 LTTit 的 `test/`，STM32 工程为 `test1/`，可在 CLion 配置 ARM 工具链和烧录后使用。[原硬件上手文档](https://github.com/skaiui2/lttit/blob/main/docs/English/quickStart.md)保留了构建和烧录路线。Pico CMake 中的 `PICO_SDK_PATH` 是绝对路径，需要对应本机 SDK；实验记录中应保存实际固件版本和编译选项。

| 用途 | 连线 | 串口参数 |
| --- | --- | --- |
| Pico → STM32 | GPIO4 TX → PA10 RX | 115200 |
| STM32 → Pico | PA9 TX → GPIO5 RX | 115200 |
| PC ↔ Pico Shell | 串口模块 TX → GPIO1 RX，RX → GPIO0 TX | 115200 |
| STM32 输出 | PA2 / USART2 TX → 另一串口模块 RX | 115200 |
| 地线 | 各端共地 | — |

待两端固件初始化完成、目标资源注册后，将上面的源码保存到 Pico 文件系统中的 `migrate.bpf`，在 Shell 输入：

```text
compile migrate.bpf
runbpf migrate.ccbpf
```

`cmd_compile()` 自动生成 `.ccbpf` 文件名。预期先在 Pico 看到 1、2、3、4，迁移后在 STM32 看到 5、6、1129 和 `STM32: finished 1129`。记录两个串口、实际烧录版本及镜像。这份路线来自已有硬件演示和源码核对，本次主机复现没有新增板上测量。

## 8. 可执行复现与结果

### 8.1 独立复现程序

`experiments/migration/migration_reproduce.c` 直接使用当前 root 编译器、VM 和 `migrate.bpf`，没有复制或修改 VM 实现。它依次：

1. 编译一次，保留独立镜像副本。
2. 执行同节点基线；遇到迁移状态后仍在同一状态上继续，直到返回。
3. 重新加载源端程序，执行到迁移，并检查已有五个数字输出、`pc-1` 是 COP 8。
4. 打包状态，卸载源端程序并覆盖原执行状态。
5. 重新加载目标端程序；先验证错误快照长度被拒绝，再恢复正确快照，比较全部状态字节。
6. 释放传输缓冲区后继续运行，比较最终 A/X/pc/ret/mem 与基线，核验输出 1..11、四个字符串标记各出现一次、返回 0。

每次复现启动一个新进程，避免把编译器全局计数器和区域句柄当成独立编译实例。打印回调取消演示中的一秒等待；结果用于正确性核验，不用于耗时评价。

GCC/Clang 的 POSIX 环境下，在仓库根目录执行：

```bash
mkdir -p /tmp/ccbpf-migration-check
cc -std=c99 -Os -include string.h \
  -IccBPF -IccBPF/vm/bpf/include \
  -IccBPF/compiler/frontend/include -IccBPF/compiler/backend/include \
  -IccBPF/compiler/ir/include -Img/include -Ilib/include \
  experiments/migration/migration_reproduce.c \
  ccBPF/compiler/frontend/source/*.c ccBPF/compiler/backend/source/*.c \
  ccBPF/compiler/ir/source/*.c ccBPF/vm/bpf/source/*.c \
  mg/source/*.c lib/source/*.c -lm \
  -o /tmp/ccbpf-migration-check/reproduce
/tmp/ccbpf-migration-check/reproduce "$PWD/migrate.bpf"
```

`-include string.h` 为当前源文件补充字符串函数声明，不修改源码。本次已验证环境是 Windows x64、MinGW GCC 13.1.0、CMake/Ninja、Release 加 `-Os`；没有在该环境执行 Linux socket 传输。Linux LP64 的指令结构大小与 MinGW 不同，镜像大小应以复现程序打印值为准。

## 9. 实现边界

原生结构拷贝要求两端指令布局、C `long` 大小、填充、字节序、scratch 容量、变量和临时值布局兼容；Native ID 的语义和参数也必须匹配。VM 源码能够移植不等于当前镜像任意跨 ABI 通用。宿主输入和外部资源需要单独重建。

快照没有版本、校验和或程序标识，解包只检查长度。加载器和解释器也没有完整的恶意输入隔离验证。本例的连续性推理以合法可信镜像、有效 pc、成功分配和兼容依赖为前提。

源端在发送前停止，root 传输没有确认、重试或执行所有权事务。断线、重复投递、目标掉电以及已发生的外部副作用，都没有自动恢复保证。LTTit 的 RPC 返回也不等同于持久化的执行所有权记录。

root demo 及 STM32 接收处理函数没有在所有完成路径调用 `ccbpf_unload()`，连续运行多次迁移需要补齐对象释放。打印的 `sleep/HAL_Delay` 用于观察，不能当作迁移时延。

## 10. 扩展实验：方法与实测结果

实验环境为 Windows 11 build 26200、AMD64 Family 25 Model 80 处理器、MinGW GCC 13.1.0。原有编译器和 VM 未改动。分别使用 `-Os` 和 `-O2`，不启用 LTO；每个程序在独立新进程中编译一次。

语料共 32 个程序：README demo、在主机运行的硬件论文程序、提前迁移/末尾迁移/两次迁移/条件为真/条件为假/字符串六个定向程序，以及固定种子 0..23 的 24 个算术程序。每个算术程序含 12 次赋值、两次迁移和最终打印。Python 独立计算预期返回值，除数非零，减法避免负中间值，乘加遵循 VM 的无符号结果。

### 10.1 正确性与新进程恢复

| 项目 | 完成结果 | 检查内容 |
| --- | --- | --- |
| 程序 × 优化模式 | 32×2，共 64 次通过 | 与独立预期返回值一致 |
| 独立检查点恢复 | 7,518 次通过 | 每种优化模式 3,759 个实际经过的指令边界 |
| 每条指令前反复迁移 | 另有 7,518 次打包、恢复及镜像重载 | 最终完整状态与基线相同 |
| 源进程退出后新进程恢复 | 10/10 通过 | 源端 1..5，目标端 6..11，返回 0 |
| 自定义分配器空闲字节平衡 | 64 次运行全部通过 | 测试结束及卸载后恢复到对应基线 |

测试先单步执行，保存每个实际经过的指令前状态，再逐个恢复、运行剩余后缀，逐字节比较最终 `ccbpf_ctx`。输出采用 64 位滚动哈希和事件计数；观察器以基线前缀状态初始化，用于比较后缀。它是测试记录器，不是声称自动迁移的宿主外部状态；哈希也不构成无碰撞的等价证明。原 README demo 另有数字序列直接检查。分支的真、假路径分别验证，没有宣称穷举所有输入和不可达指令。

`process.c` 的源进程将镜像、快照写入文件后退出，新目标进程读取文件、重新注册 Native、继续执行。实验封装包含 magic、两个小端 32 位长度和原生镜像/状态。十次实验均通过，证明该例子不依赖源进程地址空间仍然存活。这是本机文件交接，不是串口或网络性能实验，也没有替换项目协议。

### 10.2 主机操作耗时

使用 `QueryPerformanceCounter`，每个操作先丢弃三个预热批次，再记录 31 个批次。每批 1,000 次操作；加载/卸载每批 100 次。下表为批次平均耗时的中位数及 P05/P95，单位 ns；分位点取排序后 `floor(q×(n-1))` 下标。它们不是单次调用的尾延迟，也不是置信区间。

| Operation | -Os median [P05, P95], ns | -O2 median [P05, P95], ns |
| --- | --- | --- |
| 打包并释放 | 19.7 [19.7, 19.9] | 17.1 [16.9, 17.1] |
| 解包 | 17.1 [17.1, 17.3] | 17.9 [17.8, 18.0] |
| 加载并卸载镜像 | 356.0 [350.0, 361.0] | 274.0 [272.0, 278.0] |
| 完整执行程序 | 556.1 [553.6, 558.6] | 474.4 [470.2, 477.7] |

![README 程序的主机操作耗时](../../experiments/migration/results/2026-10-04/timing.svg)

打包计时包含分配、复制、读出一个字节及释放；解包包含长度检查、复制和 volatile 结果读取；加载/卸载包含验证、分配、复制和释放。完整执行包含 VM 调用、Native 查表、输出哈希及本地处理迁移状态。计时不包含终端打印、进程启动和文件交接。采用重复访问的热数据，没有扣除空循环成本或控制冷缓存；两种优化顺序运行，不能据此作严格的因果性能对比。这些是桌面主机数据，不是 STM32/Pico 迁移时延。

### 10.3 分配与异常输入

加载程序时，自定义分配器的空闲字节减少量分别是 README 程序 1,856 字节、硬件论文程序的主机版本 1,000 字节、`arithmetic_00` 1,208 字节；执行上下文均为 528 字节。减少量包含分配块开销，但不含原镜像、编译器峰值、Native 表、C 栈、观察器数组和传输缓冲区，不能写成总 RAM 峰值。

每次运行执行七项边界检查，共 448 项：

| 输入 | 实际行为 |
| --- | --- |
| 快照长度 0、正确值减 1、正确值加 1 | 三项均拒绝，目标状态保持不变 |
| 正确长度，篡改一个 scratch 字节 | 接受，恢复状态发生变化 |
| 正确长度，pc 为 0xffffffff | 解包接受；测试不执行这个非法状态 |
| 修改镜像 magic | 加载返回 NULL |
| 镜像截断为一个字节 | 加载返回 NULL |

结果说明长度校验有效，但快照完整性和 pc 合法性没有由解包器检查。测试没有执行非法 pc 或任意模糊测试字节码。分配器平衡通过仅针对复现程序明确释放的路径，不代表原 demo 的释放遗漏已经修复。

### 10.4 一条命令复现全部实验

需要 Python 3 标准库和 GCC 兼容编译器，在根目录执行：

```bash
python experiments/migration/run_experiments.py --cc gcc --out /tmp/ccbpf-migration-results
```

Windows 将 `--cc` 设置为 MinGW `gcc.exe` 的完整路径，并指定仓库外输出目录。脚本生成语料，构建两种优化版本，运行正确性、计时及十次新进程实验，输出日志、CSV 和 `summary.json`；失败返回非零。元数据包含工具链、编译命令、源码哈希和 Git 版本。耗时不要求逐次相同，语料、状态比较和语义断言是复现判据。

## 11. 适用范围与后续实验


| 问题 | 实验方法 | 应公开的数据 |
| --- | --- | --- |
| 多个迁移位置是否保持连续性 | 改变迁移点、scratch 内容、算术与兼容 Native 调用 | 源码、镜像哈希、pc、输出和状态比较 |
| 暂停到恢复需要多久 | 记录让出、打包完成、接收完成、目标首条指令；使用共同时间基准或经过测量的时钟同步 | 时间基准、样本数和分布，不能直接相减两块板的未同步时间 |
| 资源成本是多少 | 分开测量编译、执行、打包、传输和目标加载 | 固件版本、优化选项、Flash、堆和栈高水位、负载长度 |
| 传输占多少成本 | 对照本地恢复与不同大小负载的 UART/RPC 迁移 | 封装字节、重试及实际吞吐 |
| 失败后会发生什么 | 截断、错配、重复投递、断线及分配失败 | 拒绝或恢复过程、外部副作用 |
| 支持哪些板卡组合 | 固定 Pico → STM32 固件版本，再验证其他方向 | 格式、Native 绑定、两端连续日志 |

本次形成了一个有原始数据和独立返回值校验的主机实验研究。其限制是单一桌面 ABI、单一编译器版本、短程序和可信状态；计时来自预热批次平均值。新增数据支持所测语料的执行连续性和本机操作成本，板间时延、能耗、传输吞吐及故障恢复仍需各自的硬件实验。

## 12. 资料与版本

英文论文草稿与本文共享同一机制和实验口径。基础材料为 Skai Uijing 的《ccBPF: A Portable and Reproducible Embedded Programming Artifact for MCU-Class Systems》和《Live Migration of Compiled ccBPF Programs Across Heterogeneous MCUs Using LTTit》。
